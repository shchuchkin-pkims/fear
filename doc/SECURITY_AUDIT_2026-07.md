## 0. Резюме (честная оценка)

Криптографический фундамент проекта зрелый: правильные примитивы (AES-256-GCM, Ed25519, X25519, Argon2id, BLAKE2b) через libsodium, аккуратное затирание секретов, параметризованный SQL, zero-knowledge-маршрутизация без межкомнатных утечек, а Android заметно вырос (секреты в Keystore-backed EncryptedFile, `allowBackup=false`). Это хорошая база.

Но текущее состояние **нельзя называть «безопасным мессенджером»** без оговорок. Аудит нашёл **5 критических проблем**, из которых 4 – это повреждение памяти (переполнения буфера) с потенциалом удалённого выполнения кода, а 5-я – обход защиты от MITM, который сводит на нет само обещание end-to-end шифрования против недоверенного сервера. Три из этих проблем срабатывают **без знания ключа комнаты** (on-path атакующий или недоверенный relay-сервер), то есть ровно в той модели угроз, от которой продукт должен защищать.

Прошлая оценка «8.0/10» была завышена, потому что аудит не покрывал медиа-тракт, серверные команды Phase B (blob/handle) и веб-часть, а по ECDH сделал вывод по намерению, а не по факту. Реалистичная оценка сейчас: **критические дыры блокируют выпуск, но все они локальны и чинятся за 1-2 недели сфокусированной работы.** Ни одна не требует переделки архитектуры.

Важно: большинство «стратегических» проблем (forward secrecy, метаданные, replay, хранение ключей) **вы уже запланировали** в `architecture-decisions.md` (§4, §5, §13, Phase 0). План ниже не ломает вашу дорожную карту, а вставляет перед ней короткую «стоп-фазу» с memory-safety и auth-фиксами.

| Подсистема | Оценка | Ключевое |
|---|---|---|
| Крипто-примитивы | 8/10 | применены корректно; проблема в логике обмена ключом, не в примитивах |
| Протокол/обмен ключом | 4/10 | MITM жив на всех клиентах (C5), нет FS, нет channel binding |
| Медиа-тракт | 3/10 | два Critical-переполнения в «клее» дешифрования (C1, C2) |
| Серверное ядро | 6/10 | парсер кадра и SQL безопасны; но integer overflow (C3), блокирующий I/O DoS |
| Десктоп-клиент | 5/10 | переполнение стека в FILE_START (C4); stdout-инъекция бейджа |
| Веб (клиент+мост) | 4/10 | SSRF-прокси, нет CSP, sk в localStorage; XSS не найден, но модель хрупкая |
| Android | 7/10 | Keystore/at-rest хорошо; тот же MITM, логи ключей, APK без проверки |

## 1. CRITICAL (чинить до любого дальнейшего использования)

### C1. Медиа: неограниченный вывод AES-GCM в `plain[64]` → переполнение стека (unauthenticated crash / RCE)
- **Статус: подтверждено лично.** `video_call.c:696-719` (`decrypt_stats`), тот же паттерн `audio_call.c:516-539`.
- Проверка `if (pkt_len < 1+8+AES_GCM_ABYTES)` (стр.698) ограничивает длину только снизу. `crypto_aead_aes256gcm_decrypt` пишет `pkt_len-25` байт (до ~4071 при `rbuf`=`MAX_PACKET_SIZE`=4096) в `uint8_t plain[64]` (стр.708-712). Проверка `mlen < sizeof(StatsPayload)` стоит уже ПОСЛЕ записи (стр.716).
- libsodium в combined-режиме пишет открытый текст в выходной буфер и обнуляет его при неверном теге **до того**, как вернуть ошибку, поэтому переполнение происходит **даже без валидного тега**. HELLO не аутентифицирован и безусловно ставит `remote_prefix_ready=1` (`video_call.c:488`), то есть on-path атакующий **без ключа комнаты** доводит жертву в звонке до гарантированного краха; участник комнаты (со знанием ключа) получает управляемое переполнение → RCE. Достижимо по UDP и по TCP-relay.
- **Фикс:** до дешифрования отвергать пакет по верхней границе: `if (pkt_len - 9 - AES_GCM_ABYTES > sizeof(StatsPayload)) return -1;`. Дешифровать во временный буфер достаточного размера. Исправить в обоих файлах; проверить паритет в Android (`VideoCallManager`/`AudioCallManager` – Kotlin memory-safe, но логику длины выровнять).

### C2. Медиа: знаковое сравнение `clen` в TCP-relay → переполнение от недоверенного сервера (RCE, без ключа)
- **Статус: подтверждено лично.** `video_call.c:377-383` (`tcp_relay_recv_media`), тот же баг `audio_call.c:435-441`.
- `if (type == MSG_TYPE_MEDIA_RELAY && (int)clen <= out_size && clen > 0)` – каст `(int)clen`. При `clen >= 0x80000000` результат отрицателен, условие истинно, и `tcp_recv_all(out, clen)` принимает до ~2-4 ГБ в маленький буфер (`rbuf`).
- Канал до relay идёт **без TLS**, а relay в вашей модели недоверенный. Вредоносный/скомпрометированный сервер или MITM на пути шлёт кадр `MEDIA_RELAY` с задранным `clen` → переполнение с полностью контролируемым содержимым, **ключ комнаты не нужен** (это внешняя TCP-обёртка). Куча (видео) / стек (аудио).
- **Фикс:** сравнивать без знака и с явной верхней границей: `if (type == MSG_TYPE_MEDIA_RELAY && clen > 0 && clen <= (uint32_t)out_size)`. Ограничить `clen` разумным медиа-максимумом.

### C3. Сервер: integer overflow в проверке длины BLOB_PUT → удалённый краш всего relay одним пакетом
- **Статус: подтверждено лично.** `server.c:489-510`.
- `cipher_len` (4 байта из payload) – единственное поле команд, не ограниченное `MAX_FRAME`. Проверка `if (clen < (uint32_t)32+64+1+type_len+4+cipher_len)` (стр.495) считает правую часть в `uint32_t`: при `cipher_len=0xFFFFFFFF`, `type_len=0`, `clen=101` сумма оборачивается в 100, `101 < 100` ложно → проверка пройдена. Далее `signed_len = 0xFFFFFFFF`, `malloc(~4ГБ)` (при дефолтном overcommit проходит), `memcpy` читает ~4 ГБ из ~101-байтного буфера (стр.510) → SIGSEGV. Подпись проверяется на стр.511, уже после. Аутентификация не нужна.
- Сервер однопоточный → падает весь relay, все ≤100 клиентов. (Старый аудит blob-команды не покрывал.)
- **Фикс:** `uint32_t header = 32+64+1+type_len+4; if (clen < header || cipher_len > clen - header) { reject; }`. Плюс общий приём: ограничить `cipher_len <= MAX_FRAME`.

### C4. Десктоп-клиент: переполнение стека имени файла в FILE_START (RCE от участника комнаты)
- **Статус: подтверждено лично.** `client.c:752-757`.
- `uint16_t fn_len = rd_u16(p);` (до 65535), затем `memcpy(orig_filename, p, fn_len)` в `char orig_filename[MAX_FILENAME]` (1024) **без единой проверки границ**, плюс `orig_filename[fn_len]='\0'` далеко за буфером. Для FILE_CHUNK/FILE_END проверки длины есть, для FILE_START – нет.
- Участник комнаты (у него есть общий ключ) шлёт FILE_START с `fn_len=65535` → переполнение стека ~64 КБ у всех получателей. Для SIGNED_FILE_START провал подписи обработку НЕ останавливает (`client.c:1298-1314`). В связке с отсутствием stack-protector (M1) – реальный путь к RCE. Далее `file_size`/`crc` тоже читаются без проверки, что `plen` их покрывает (heap over-read).
- **Фикс:** `if (plen < 2) return; fn_len = rd_u16(p); if (fn_len > plen-2 || fn_len >= MAX_FILENAME) return;` до memcpy; аналогично прикрыть чтение размера/CRC.

### C5. ECDH: приём ключа комнаты при провале/отсутствии подписи → MITM жив на ВСЕХ клиентах (F8 не исправлен)
- **Статус: подтверждено лично (десктоп), агентами (веб, Android).**
- Десктоп `client.c:285-295`: `crypto_box_open_easy(...)` и `result=0` выполняются **независимо от `sig_verified`**. Если блок подписи отсутствует (`remaining < PK+SIG`, стр.258) – проверка пропущена молча; если подпись невалидна (стр.280-282) – только warning в stderr; ключ всё равно принят. Вызов на стр.~1550 проверяет только `!= 0`.
- Веб `app.js:322-348` и Android `FearClient.kt:640-698` – та же логика: подпись опциональна и не блокирует приём.
- Плюс подпись покрывает только эфемерный X25519 (`client.c:365`), без привязки к комнате/джойнеру/шифртексту (нет channel binding), а TOFU ведётся по отображаемому имени из фрейма, которым управляет сервер.
- Недоверенный relay (или участник, ответивший на KEY_REQUEST первым) отвечает своим `crypto_box` с известным себе ключом комнаты и без/с мусорной подписью → джойнер принимает ключ атакующего → полный MITM переписки. Ed25519-подпись на сообщениях это не ловит: атакующий переоборачивает тот же подписанный plaintext. Это подрывает центральное обещание zero-knowledge-модели.
- **Фикс:** сделать подпись **обязательной и блокирующей**: приём ключа только при `sig_verified == 1`. При отсутствии подписи/identity у стороны – прерывать обмен (или явный `--insecure`). Подписывать транскрипт `sign(eph_pk || room || joiner_pk || box_nonce || box_cipher)`. TOFU-конфликт («ключ изменился») тоже должен блокировать, а не предупреждать. Исправить на трёх клиентах согласованно.

## 2. HIGH

- **H1. Апдейтер без проверки подписи + CI-релизы без подписи.** `updater/src/updater.c` скачивает ZIP с GitHub → `unzip` → rsync поверх бинарников → запуск, без minisign/GPG/контрольных сумм; `.github/workflows/*.yml` публикуют ZIP без подписи. Компрометация релиз-канала = произвольный код у всех пользователей. Для инструмента против блокировок это ключевой риск. **В вашем roadmap уже отмечено (minisign, Phase 0) – нужно снять с «отложено».** Фикс: minisign-подпись в CI + обязательная проверка в апдейтере до установки.
- **H2. Zip-Slip в апдейтере.** `updater.c:580-598`: извлечение недоверенного архива через `unzip -o` + rsync содержимого; path-traversal зависит от версии unzip, в связке с H1 = полная компрометация. Фикс: извлекать своей библиотекой с проверкой путей записей.
- **H3. Веб-мост = неаутентифицированный открытый TCP-прокси (SSRF).** `web/server.js:82-106`: `host`/`port` из браузера без allowlist/блокировки приватных диапазонов → connect на любой host:port; оракул ошибок (стр.128-133). High, Critical в облаке (IMDS 169.254.169.254). Скан внутренней сети, open-proxy от IP `fear-project.ru`. Фикс: allowlist целевого хоста, резолв DNS + блок приватных/loopback/link-local ДО connect (анти-rebinding), не отдавать `err.message`.
- **H4. Веб: нет CSP и security-заголовков.** Нет `Content-Security-Policy`, HSTS, X-Frame-Options (`index.html`, `server.js:21` express.static без helmet). В E2E-модели CSP – единственная страховка от кражи ключей при будущем XSS; её нет вообще. Фикс: helmet + жёсткий CSP + HSTS.
- **H5. Нет forward secrecy; статичный ключ комнаты; ЛС-ключ из долгосрочных Ed25519.** `identity.c:351-390`, `client.c:1544-1558`. Компрометация ключа раскрывает всю прошлую+будущую переписку. **Совпадает с вашим планом §5 (K_epoch, Phase C)** – сейчас просто отсутствует. Фикс: ротация ключа + эфемерный вклад / ratchet.
- **H6. Сервер: блокирующий I/O в однопоточном select-цикле → slowloris-DoS.** `server.c:81-149` (`read_frame` серией блокирующих `recv_all`), нет `SO_RCVTIMEO`/`SO_SNDTIMEO`. Одно соединение, «капающее» по байту, замораживает весь сервер; «медленный читатель» на `send_all` – тоже. Фикс: неблокирующие сокеты + конечный автомат чтения, либо таймауты на каждый клиентский сокет.
- **H7. GUI: инъекция перевода строки в stdout подделывает бейдж `[V]`/имя отправителя.** `backend.cpp:514` режет stdout CLI по `\n` и доверяет маркерам `[V]/[T]/[!]`, `[TOFU]`, `[FILE_OFFER]`. Приём в CLI не санитизирует plaintext (`client.c:1198` печатает `%.*s`), поэтому вложенный байт 0x0A даёт вторую строку `[..] [V] Alice: ...` → GUI рисует поддельно-верифицированное сообщение, имперсонация доверенных участников. Обходит всю Ed25519/TOFU-индикацию. Фикс: не использовать stdout как канал управления – структурированный IPC или экранирование управляющих символов на приёме в CLI.
- **H8. Медиа: неограниченный вывод AES-GCM для Opus.** `audio_call.c:645,701` (`opus[1275]`), `video_call.c:951,1019`. До ~1475 байт в 1275-байтный буфер, тот же паттерн, что C1 (запись до сверки тега). Фикс: передавать размер выходного буфера и проверять до дешифрования.

## 3. MEDIUM (сгруппировано)

**Крипто/ключи**
- M1. Компиляция без hardening-флагов (`CMakeLists.txt:9`, Dockerfile): нет `_FORTIFY_SOURCE=2`, `-fstack-protector-strong`, PIE, RELRO, noexecstack. Прямо усиливает C1-C4. Дёшево. Фикс: добавить флаги.
- M2. Десктоп: Ed25519 sk на диске открытым текстом; `chmod 0600` ПОСЛЕ создания (TOCTOU); Windows без ACL (`identity.c:104-117`). Android это уже закрыл (Keystore). Фикс: `open(O_CREAT|O_EXCL,0600)`; DPAPI на Windows.
- M3. Аудио: один ключ на оба направления, разделение лишь 4-байтным prefix; нет replay-окна; `seq` рестартует с 0 (`audio_crypto.c:34-43`, `audio_call.c:994`). Коллизия prefix ~2^-32/звонок → nonce reuse GCM. Фикс: раздельные подключи по роли (caller/callee) + sliding-window replay; для аудио на Android – использовать `deriveAudioKey` как в видео.
- M4. Аудио-TOFU по хардкод-имени "peer" (`audio_call.c:231`) → ложные KEY_CONFLICT, бесполезная проверка в звонках. Фикс: ключевать по стабильному id.
- M5. Медиа: nonce-prefix 4 байта + детерминированные ключи → риск reuse при накоплении сессий (~2^16). Фикс: соль сессии в KDF, либо XChaCha20-Poly1305 (24-байтный nonce).
- M6. Медиа: нет replay-защиты (аудио/видео/stats). **Совпадает с §13 (Phase D)** – но стоит подтянуть раньше, т.к. медиа – место RCE.

**Сервер**
- M7. Нет лимита соединений на IP (MAX_CLIENTS=100) → исчерпание слотов (`server.c:924-936`).
- M8. Blob-хранилище без квот → исчерпание диска (Ed25519-ключи генерируются бесплатно, `server_db.c:202-217`). **Совпадает с квотами §7 (Phase B).**
- M9. Сервер не перепривязывает `name` на ретранслируемых кадрах → спуфинг отправителя для unsigned TEXT (`server.c:166-201`). Фикс: перезаписывать `room`/`name` зарегистрированными значениями.

## 4. LOW / INFO

- L1. Fingerprint 64 бита (`identity.c:392-404`) – коротко для ручной верификации; показывать >=128 бит.
- L2. Directory-сервер доверенный: lookup handle→pk без подписи (`server_proto.c:177-214`).
- L3. Неподписанный/невалидно-подписанный текст всё равно отображается (маркеры `[?]`/`[!]`) – совещательная аутентичность.
- L4. identity_backup: KDF-параметры из недоверенного `.fbk`, cap memlimit 1 ГБ → OOM (`identity_backup.c:167-175`). Иначе backup-крипто корректно.
- L5. key-exchange.c standalone пишет sk открытым текстом (`:508-543`) – demo-утилита, если не используется в проде – пометить.
- L6. Апдейтер: хрупкий относительный `cacert.pem`, вводящие в заблуждение комментарии, `system("cd")`, безлимитный realloc.
- L7. Docker: base-образ не запинен по digest; нет VOLUME для БД (non-root + multi-stage – хорошо).
- L8. Off-by-one на границе MAX_ROOM/MAX_NAME==256 (`server.c:88,101` проверяют `>`, не `>=`) → OOB-чтение соседнего поля структуры.
- L9. Android: legacy `MainActivity` exported без intent-filter; FileProvider раздаёт весь cacheDir; аудио использует сырой room key вместо подключа; полный room key в DEBUG-логах.
- L10. Неаутентифицированный HELLO (`video_call.c:475-524`, `audio_call.c:217`) → подмена nonce-prefix, трэшинг декодера (DoS); плюс это предусловие эксплуатации C1/H8.
- L11. Hub/relay: неаутентифицированное участие, room/name открытым текстом (`audio_hub.c`, TCP-регистрация) – утечка метаданных, площадка для инъекций.

## 6. Что сделано хорошо (для баланса)

- Примитивы через libsodium применены в основном корректно; AAD связывает room+name; свежий random nonce на обычных send-путях.
- Затирание секретов `sodium_memzero` на всех путях (identity, эфемерные X25519).
- **Парсер внешнего кадра `read_frame` безопасен по памяти** (все длины проверены до использования); **SQL полностью параметризован** (`sqlite3_bind`, whitelist символов handle); нет format-string, нет `system/exec` из сети.
- **Реассемблер видеофрагментов безопасен** (явная проверка `offset+frag_size > frame_buf_size`, `video_fragment.c:192`) – вопреки ожиданиям, самый крепкий участок. HELLO-размеры не используются для аллокаций (нет DoS «гигантским разрешением»).
- Android: секреты в Keystore-backed EncryptedFile с миграцией без tmp+rename, `allowBackup=false`, Argon2id-бэкап с cap против OOM, нет WebView, сервисы не экспортированы, пароли keystore в `local.properties`.
- Веб: сетевые данные экранируются, эксплуатируемого XSS не найдено; sodium.js локально (не CDN).
- Docker: non-root, multi-stage; git-гигиена чистая (БД/архивы в `.gitignore`, реальных ключей в репо нет).
- Продуманный roadmap (`architecture-decisions.md`) уже учитывает FS, метаданные, replay, квоты, key storage.

## 7. План исправления

Принцип: короткая **стоп-фаза** с memory-safety и auth перед продолжением вашего Phase-плана. Остальное ложится в уже существующие Phase 0-F.

### Phase −1 – СТОП-фиксы (дни, до продолжения Phase B) ★★★
Всё это – локальные правки, не архитектура.
1. **C1 + H8**: верхняя граница длины ДО дешифрования в `decrypt_stats` и Opus-путях (audio+video), паритет в Android.
2. **C2**: беззнаковое сравнение `clen` + верхний лимит в `tcp_relay_recv_media` (audio+video).
3. **C3**: не-переполняющаяся проверка длины BLOB_PUT (`server.c`).
4. **C4**: bounds-check `fn_len`/размера/CRC в FILE_START (`client.c`), паритет в Android-парсере.
5. **C5**: обязательная блокирующая проверка подписи в ECDH на трёх клиентах + channel binding подписи.
6. **M1**: hardening-флаги компилятора (CMake + Dockerfile) – 30 минут, снижает эксплуатабельность остатков.
7. **H7**: закрыть stdout-инъекцию бейджа (структурированный IPC или санитизация 0x0A в CLI).
8. Быстрый прогон тестом: фаззинг парсеров кадра/пакета (AFL/libFuzzer) на server.c, client.c, audio/video decrypt.

### Phase 0 – security baseline (расширить существующий) ★★★
- **H1 + H2**: minisign-подпись артефактов в CI + обязательная проверка в апдейтере; Zip-Slip. (У вас уже в плане как «отложено» – снять.)
- **M2**: шифрование identity_sk на диске на десктопе (Android готов).
- **Веб-решение (H3, H4, M11-M15)**: либо снять публичный мост до харденинга, либо: allowlist целевого хоста + блок приватных диапазонов, Origin-check, rate-limit/`maxPayload`/timeout, helmet+CSP+HSTS, sk под парольной фразой, подтверждение скачивания. И честно позиционировать веб как «канал пониженного доверия» (оператор сервера может подменить крипто-код – это не полноценный E2E против хоста).

### В существующие фазы roadmap
- **Phase B (§7 сервер):** M7 (лимит на IP), M8 (квоты blob), H6/M20 (неблокирующий I/O + таймауты), M9 (перепривязка name), M10 (BLOB_GET auth). Плюс UX-перестройка §10: **исправить онбординг** (авто-identity, не блокировать Connect), один UI, честный статус, прогресс файлов, модальное MITM-предупреждение.
- **Phase C (§5 крипто):** H5 (FS/ротация ключа), M3/M5 (раздельные подключи, соль сессии/XChaCha20). Самое рискованное – тест-векторы до кода.
- **Phase D (§4/§13):** M6 (replay медиа – желательно раньше), replay сообщений, opaque room_id/sender_alias, L1 (длинный fingerprint), L8/L10/L11.
- **Android-гигиена (параллельно):** M16 (логи+minify), M17 (проверка APK), M18 (уведомления), M19 (лимит длины), M21 (убрать MANAGE_EXTERNAL_STORAGE).

### Оценка трудозатрат (solo, свободное время)
- Phase −1: ~1-2 недели (правки локальные, но требуют аккуратности и тестов на 3 клиентах).
- Phase 0 (подпись релизов + веб-харденинг + desktop key storage): ~1-2 недели.
- Дальше – по вашему графику 10-13 недель до v0.6.0, куда остальное уже вписано.

**Вывод:** проект строится грамотно и близок к цели, но прямо сейчас «безопасным» его называть рано – 5 критических дыр (4 memory-corruption + обход MITM) блокируют использование. Хорошая новость: все они локальны, и после Phase −1 + Phase 0 продукт можно давать друзьям с честной формулировкой гарантий. Начинать строго с Phase −1.
