## What's New in v0.6.0

This release completes Phases C–F of the [roadmap](https://github.com/shchuchkin-pkims/fear/wiki/Roadmap): the room key now follows the room, the relay no longer learns room names or display names, calls work for groups, and messages reach contacts who are offline.

> **Not compatible with v0.5.x.** The wire format changed – rooms travel hashed, participants as random session tags, chat under a new key schedule, calls under new framing. Update every device **and the relay** together.

### Encryption

- **The room key rotates on every change of membership.** One member, chosen the same way by every client, draws a new generation and seals it to each member's identity key. A newcomer cannot read what was said before they arrived; a member who left cannot read what is said after.
- Chat is sealed under per-epoch keys derived from the current generation (`key_version` + `epoch` in every frame); during a change, receivers hold two generations, so nothing in flight is lost.
- **Group calls with per-sender keys.** Every participant encrypts under a key of their own for that call; announcements (HELLO2) are authenticated, and every sender has its own replay window. A call is announced to the room with a fresh call id over the encrypted chat.
- The desktop **identity key is encrypted at rest** – wrapped by a key in the system keyring (libsecret) or protected by DPAPI on Windows. Where there is no keyring, the file stays readable only by you, and the program says so.
- **One fingerprint per key, on every platform** (BLAKE2b, 8 bytes; the short `name#xxxxxxxx` is its first 4 bytes). Until now the desktop core, the desktop profile window and Android computed three different values for the same key.
- Encrypted contact blobs can only be read by their owner (signed one-shot challenge).
- A modal warning when a peer's identity key changes.

### Metadata privacy

- **The relay no longer sees room names.** On the wire a room is `r:` + a hash of its name. The `pm:` prefix that set personal chats apart is gone, and the identifier of a personal chat is derived under the pair's key – the relay cannot compute whose chat it is.
- **The relay no longer sees display names.** A connection introduces itself with a random 16-byte tag, new every time; the real name travels inside the encryption, in an announcement signed together with the tag. Calls use the same tags.
- **Optional TLS** to the relay (`--tls`, `--tls-pin`, `--tls-cert`/`--tls-key`): on-path observers stop seeing F.E.A.R. frames. It hides nothing from the relay itself, and the settings say so.

### Offline inbox

- A message to a contact who is not online waits on the relay, sealed, under an address only the two of you can compute. Clients collect waiting messages for all contacts in one request.
- Retention is the operator's choice: `fear server --inbox 30d | Nh | off` (30 days by default; at most 200 messages or 5 MB per recipient). The client reports a message as undelivered when that time runs out instead of pretending.

### Calls

- **Group voice** (a decoder and a jitter buffer per participant, mixed) and **group video** (active speaker large, the others in a strip) on desktop and Android.
- **Names under the video tiles** instead of session codes (the desktop video window transliterates Cyrillic – its font is ASCII-only).
- The relay sends media only to call connections – no longer into chat sockets or back to the sender. In a three-device test the video round-trip time fell from a 703 ms median to about 70 ms.
- Calls end cleanly when you hang up: the call programs handle SIGTERM and no longer hang in a quiet call, so keys are wiped and the camera is released.
- Stale video is dropped instead of queued.
- **Noise suppression** and microphone sensitivity (desktop: high-pass filter and noise gate; Android: the system suppressor, now switchable). Manual video settings (resolution, frame rate, bitrate).
- **Optional direct calls via STUN** – off by default: a direct path reveals your IP address to the people you call.

### Desktop

- **One window.** The classic interface is gone; what only it had – running a local relay, manual key exchange, chat font, the manual, the tray icon – moved over first. Closing the window hides it to the tray; Quit exits.
- Light theme by default, a date above each day, new icons; the identity is created on first run; honest connection status; file transfer progress.
- The application looks for its programs only next to itself – never in the working directory or on PATH, which could have run someone else's binary.

### Relay

- One frame parser for the server, fuzzed together with the other parsers that read the network before anything is trusted.
- Load-tested: about 365,000 relayed frames per second with a full room; the connection caps (16 per address, 100 in total) verified.
- `fear_admin` – a Qt utility for the relay's database on the same machine: handles, blobs, inbox, blocked keys, live sessions. No network interface by design.
- The Docker image ships the license texts and OCI labels.

### Downloads

- `fear-windows-x86_64-v0.6.0.zip` – extract into a folder of its own and run `fear_gui.exe`. Not code-signed: SmartScreen shows "Unknown publisher" – "More info" → "Run anyway".
- `fear-linux-x86_64-v0.6.0.zip` – extract and run `./fear_gui`. Built on Ubuntu 22.04, runs on Ubuntu 22.04+ and Debian 12+; `README.txt` lists the packages to install. FFmpeg and SDL3 are built in.
- Server image: `ghcr.io/shchuchkin-pkims/fear-server:v0.6.0` (linux/amd64, linux/arm64).

Every archive is signed (`.sig`, Ed25519); the built-in updater refuses anything else.

**The archives are complete for the first time.** Until now they held only `fear` and `fear_gui`, and not where the application looked for them: an archive from this page could not even chat, and had no calls or updater. They now carry everything the application starts, in the layout it and the updater expect, with the manual (rewritten for 0.6.0) and the license texts. The Windows archive is renamed `fear-windows-x86_64-*` – the name the updater looks for.

### Known Limitations

- **No post-compromise security** (no Signal-style ratchet) – deliberately out of scope for this release. Whoever obtains a room key reads that room until the next rotation.
- **The room hash has no secret in it:** a determined relay operator can test guesses such as "general".
- **Identity announcements** ride the room's founding key, which every member who ever joined holds: a former member who also had the relay's traffic could learn who is in the room, though not what is said.
- **The relay still sees IP addresses**, timing and sizes. Use VPN/Tor or your own relay if that matters.
- The offline inbox is collected by polling, not pushed: instant delivery would require the relay to know who is online by name.
- NAT traversal is a single STUN candidate, not ICE; not yet on Android.
- On weak Wi-Fi (especially 2.4 GHz) video may still stutter.
