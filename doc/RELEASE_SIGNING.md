# Подпись релизов

Апдейтер больше не устанавливает обновление без корректной подписи Ed25519.
Раньше он скачивал ZIP с GitHub, распаковывал и копировал поверх бинарников -
то есть любой, кто мог опубликовать релиз или подменить артефакт, получал
выполнение произвольного кода у всех пользователей. TLS доказывает лишь, что мы
говорили с GitHub, но ничего не говорит о том, кто собрал файл.

Схема простая: рядом с архивом публикуется файл `<архив>.sig` - base64
отсоединённой подписи Ed25519 над сырыми байтами архива. Публичный ключ лежит в
`updater.conf`, секретный - в GitHub Secrets.

---

## Первоначальная настройка (один раз)

### 1. Сгенерировать ключевую пару

```bash
cd build && cmake .. && make fear-sign
./updater/fear-sign keygen
```

Команда напечатает две строки base64: `PUBLIC` и `SECRET`.

### 2. Публичный ключ - в updater.conf

```
pubkey=<строка PUBLIC>
```

Этот файл распространяется вместе с приложением (CMake копирует его в
`build/bin/updater.conf`). Публичный ключ не секрет.

### 3. Секретный ключ - в GitHub Secrets

Settings → Secrets and variables → Actions → New repository secret:

- Имя: `FEAR_SIGN_KEY`
- Значение: строка `SECRET`

**Секретный ключ никогда не коммитить.** Потеря ключа означает, что все
установленные клиенты перестанут принимать новые релизы, пока пользователи
вручную не обновят `updater.conf` с новым публичным ключом. Сделайте офлайн-копию.

---

## Как это работает в CI

Оба workflow (`linux.yml`, `windows.yml`) при пуше тега `v*`:

1. собирают `fear-sign` из `updater/tools/fear-sign.c`;
2. подписывают архив, получая `<архив>.sig`;
3. прикладывают к релизу и архив, и подпись.

Если секрет `FEAR_SIGN_KEY` не задан, сборка **падает намеренно**, чтобы
неподписанный релиз не уехал к пользователям.

## Подписать вручную

```bash
FEAR_SIGN_KEY='<секретный ключ base64>' ./updater/fear-sign sign fear-linux-x86_64.zip \
    > fear-linux-x86_64.zip.sig
```

---

## Что проверяет апдейтер

1. В `updater.conf` есть `pubkey`, иначе - отказ (fail closed).
2. В релизе есть ассет `<архив>.sig`, иначе - отказ.
3. Подпись проходит проверку по публичному ключу, иначе - отказ и удаление
   скачанного файла.
4. В архиве нет путей, выходящих за каталог распаковки (Zip Slip): записи с
   `..`, начинающиеся с `/` или `\`, либо с буквой диска - отказ.

Только после всех четырёх проверок архив распаковывается и копируется.

---

## Известная проблема: имена ассетов не совпадают

Апдейтер ищет ассет строго с именем `<asset_prefix>-<os>-<arch>.zip`, то есть
`fear-linux-x86_64.zip`. А CI публикует имя **с тегом**:
`fear-linux-x86_64-v0.5.0.zip`.

Из-за этого авто-обновление не находит ассет и завершается ошибкой «Suitable
asset not found in release» - и так было ещё до внедрения подписи. Нужно
выбрать одно из двух:

- убрать тег из имени архива в CI (`name="fear-linux-x86_64.zip"`), либо
- научить `updater.c` искать ассет по префиксу, а не по точному имени.

Пока это не сделано, авто-обновление не работает независимо от подписи.
