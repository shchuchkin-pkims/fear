# Администрирование ретранслятора

`fear_admin` — утилита с графическим интерфейсом для базы, которую ведёт
`fear server`. Работает на той же машине, что и сервер: открывает тот же файл
SQLite, а не копию.

## Чего в базе нет

Переписки. Ретранслятор пересылает сообщения на лету и не хранит ни тел, ни
того, кто кому писал, — это видно и по схеме: таблиц с сообщениями в ней
просто нет. Хранится ровно две вещи:

* **занятые имена** — `@ник` и открытый ключ, за которым он закреплён;
* **блобы** — данные, которые клиент зашифровал сам (сегодня это список
  контактов). Сервер их прочитать не может, утилита показывает только размер,
  тип и время обновления.

К ним добавились две служебные таблицы, которые ведёт сам сервер:
заблокированные ключи и витрина живых подключений.

## Запуск

```
fear_admin [путь-к-базе]
```

Путь берётся из аргумента, затем из `FEAR_SERVER_DB`, затем
`./fear-server.sqlite` — тот же порядок, что и у сервера, так что запуск из
его рабочего каталога просто работает.

Останавливать сервер не нужно: база в режиме WAL, короткие записи утилиты
ждут своей очереди по `busy_timeout`.

## Что можно делать

* **Пользователи** — список занятых имён с отпечатками ключей и датой
  регистрации, поиск, выгрузка в CSV или JSON.
* **Освободить имя** — запись удаляется, ключ владельца не трогается. Имя
  сразу может занять другой ключ, и собеседники увидят привычный `@ник` за
  чужим ключом; утилита предупреждает об этом до, а не после.
* **Блобы** — просмотр и удаление. Удаление необратимо для сервера:
  восстановить сможет только сам клиент из локальной копии.
* **Блокировки** — чёрный список ключей.
* **Сейчас в сети** — кто подключён, в какой комнате и с какого адреса.
  Обновляется каждые пять секунд. Если сервер остановлен, утилита это скажет:
  он отмечается живым каждые несколько секунд и сообщает свой период прямо в
  базе.
* **Сводка** — счётчики, занимаемое место, `VACUUM`.

## Что означает блокировка ключа

Ровно то, что сервер в состоянии проверить, и не больше.

Ретранслятор видит личный ключ только там, где протокол ему этот ключ даёт:
при регистрации имени, при поиске по ключу и в подписанном запросе к блобам.
Ключа обычного подключения он не видит никогда — участники объявляют свои
личности внутри шифрования комнаты, а не серверу.

Поэтому блокировка:

* **не даёт** занять имя, найтись по ключу и хранить блобы;
* **не мешает** войти в комнату, потому что сервер не может определить, что
  вошли именно с этого ключа.

Сделать так, чтобы мешала, значило бы потребовать от каждого клиента
доказывать серверу свою личность при подключении — то есть выдать оператору
ровно тот список «кто сейчас с кем разговаривает», которого вся остальная
схема старается не создавать. Это осознанный размен, а не недоделка.
